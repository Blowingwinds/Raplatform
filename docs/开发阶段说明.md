# 自动化渗透测试平台开发阶段说明

> 本文是项目的长期开发说明。每次开始开发前先阅读本文，再阅读 `docs/开发进度.md`。新 Agent 的身份和协作规则见 `docs/Agent身份提示词.md`。

## 1. 项目目标

构建一个由云端大模型负责任务理解与编排、由 Agent 平台接入异构能力、由 MCP 负责能力调用治理、由目标黑板维护共享真值的自动化渗透测试原型。

系统的第一版目标是跑通一条可演示的闭环：

```text
测试目标与授权范围
  -> 云端大模型生成 PTT 任务树
  -> ATT&CK / 策略校验
  -> Agent 能力匹配
  -> MCP 调用信息搜集 Agent
  -> 结果归一化
  -> 目标黑板更新网络事实
  -> 触发后续任务
  -> 拓扑与发现报告
```

第一版以公司自有系统和受控靶场为授权边界，允许通过专用 Agent 进行高危漏洞发现和受控验证，包括在逐目标批准后进行 RCE 验证或 shell 上传并利用验证；不进行后渗透阶段工作。

受控靶场 Demo 使用测试账号与测试密钥，允许将验证成功的凭证值明文写入黑板 Fact 和原始 Evidence。生产环境接入真实凭证前必须另行设计保密存储和访问控制。

## 2. 核心设计约束

以下约束来自 `docs/核心设计思路.txt`，后续实现不得绕过：

1. 任务编排采用 `Goal -> Tactic -> Technique -> Action` 四级 PTT 模型。
2. ATT&CK 知识用于限制和校验编排结果；云端大模型不能直接决定任意工具调用。
3. `Action` 是结构化任务契约，不是平台维护的具体命令或渗透算子模板。
4. Agent 通过平台注册能力，通过 MCP 暴露调用接口。
5. 目标黑板是多 Agent 共享环境状态的唯一真值来源。
6. 原始执行结果与归一化事实分开保存，原始结果用于证据、审计和复核。
7. 任务执行必须经过授权范围、风险策略、租约和审计检查。
8. 高风险动作必须支持 HITL 暂停和人工批准。

## 3. MVP 范围

### 3.1 必须实现

- 项目、授权范围和任务生命周期。
- `BlackboardFact` 事实模型及版本化事件记录。
- Evidence 原始证据保存和事实来源关联。
- Agent Registry 能力注册与查询。
- MCP Gateway 的 Mock 调用、Schema 校验和审计记录。
- 云端 LLM Provider 接口，以及可重复测试的 Mock Planner。
- PTT 任务树生成、结构校验和状态流转。
- Agent Router 的能力、范围和负载匹配。
- Lease 基础租约和冲突拒绝。
- 信息搜集 Agent、网络拓扑 Agent、漏洞探测/利用 Agent、报告 Agent 四个演示 Agent。
- 黑板更新后触发后续任务的最小重编排流程。
- 网络拓扑、服务发现和证据引用报告。

### 3.2 暂不实现

- 自建渗透算子库和命令模板库。
- 任意命令生成、任意工具执行和未授权目标访问。
- 完整 ATT&CK 知识库及复杂 RAG 基础设施。
- 生产级分布式消息队列和跨节点一致性协议。
- 多租户计费、插件市场和完整权限中心。
- 后渗透阶段工作、持久化和权限维持自动化。
- 任意命令执行入口和未声明边界的 Payload 执行。

## 4. 分阶段开发流程

每个阶段都必须有可运行的产物和明确的退出条件。后续阶段不得以“先把接口留着”为理由跳过前置契约。

### 阶段 0：项目基线与边界

**目标**：建立可重复运行的项目骨架，冻结 MVP 边界和安全边界。

**工作内容**：

- 确定后端、存储、任务执行和测试方式。
- 建立源代码、测试、文档和演示数据目录。
- 固化授权范围、风险等级和 Mock 执行原则。
- 以核心设计文档和模块图作为架构基线。

**退出条件**：新环境可以启动服务并运行一个最小健康检查；项目中不存在未说明的临时指导文件。

### 阶段 1：领域模型与接口契约

**目标**：先定义模块之间传递什么数据，再实现业务逻辑。

**核心对象**：

```text
Project
Scope
TaskNode
AgentCapability
ExecutionSession
BlackboardFact
BlackboardEvent
Evidence
Lease
AuditEvent
```

**必须确定的接口**：

- PTT 任务节点输入、输出和状态枚举。
- Agent 能力声明和 MCP 调用请求/响应 Schema。
- 黑板事实的类型、来源、置信度、版本和时间。
- Evidence 与 Fact、Session、TaskNode 的关联方式。

**退出条件**：使用固定 JSON 样例可以完成 Schema 校验，且核心对象能在 SQLite 中保存和读取。

### 阶段 2：目标黑板与证据链

**目标**：实现网络状态的共享真值和原始证据追溯。

**工作内容**：

- 写入、查询和版本化 BlackboardFact。
- 记录 Fact 新增、更新、失效和冲突事件。
- 保存 Agent 原始 JSON、日志和截图等 Evidence 元数据。
- 支持按资产、服务、事实类型和版本查询。
- 发布黑板态势增量供编排器消费。
- 首批支持资产、子域名、服务、网络关系、漏洞和凭证验证事实；其他类型通过明确的身份字段扩展。
- Agent 将 Python 脚本或 Nmap 输出解析为结构化观察，平台保存原始输出并归一化为事实。

**退出条件**：Mock 信息搜集结果经过归一化后能写入黑板，并能从事实反查原始证据。

### 阶段 3：Agent Registry、MCP Gateway 与实战扫描验证

**目标**：把 Agent 当成可注册、可发现、可治理的外部能力，并在公司自有系统和受控靶场上完成真实扫描、Web 漏洞探测和受控验证。

**工作内容**：

- 注册 Agent 标识、版本、能力、输入输出 Schema、风险和并发限制。
- 查询支持指定任务契约的 Agent。
- 在 MCP Gateway 中执行已确认目标范围、Schema、风险等级、超时、取消、并发限制和审计校验；高风险调用还需最小人工批准和 Lease 检查。
- 建立 Mock Transport 和真实 MCP Transport，真实工具执行由专用 Agent 封装，不向模型或用户暴露任意命令入口。
- 信息搜集 Agent 实际扫描授权目标的资产、端口、服务、Web endpoint，并保存工具原始输出和结构化观察。
- 漏洞探测/利用 Agent 覆盖常见 Web 风险类别的候选发现与验证，包括认证/授权、输入注入、文件处理、服务端请求和配置暴露；每项能力声明目标类型、风险、请求预算、副作用和停止条件。
- 对 WAF 拦截绕过提供受控的策略变体能力，逐次记录尝试与响应；只在已确认范围和请求预算内运行，不把绕过结果当作漏洞成立证据。
- 将 RCE 验证、shell 上传及利用验证作为独立高风险能力，仅在明确批准的目标上执行最小化证明，记录副作用并清理测试产物。
- 公司系统使用指定测试账号或凭据引用；敏感原始 Evidence 需加密保存，BlackboardFact 和审计日志只保留引用与脱敏摘要，真实凭据和会话密钥不得明文落库。
- Agent 输出经现有 Evidence 和 Blackboard 服务保存，漏洞候选与验证结论分开表达，能回查原始请求、响应和工具日志。

**退出条件**：信息搜集与漏洞探测/利用 Agent 可注册、发现并通过 Gateway 调用；授权靶场中完成真实扫描、至少两类 Web 风险候选发现、一项受控验证和一次 WAF 拦截策略变体测试，结果能回查 Evidence；越界、未批准高风险调用、Lease 冲突、超时和取消均有拒绝或停止记录。再于单独确认范围、动作和运行窗口的公司自有系统完成一次实际扫描与非破坏性验证，证明该能力可直接使用。

### 阶段 4：PTT 编排与云端模型适配

**目标**：将用户目标转成受约束的结构化任务树。

**工作内容**：

- 定义云端模型 Provider 接口和结构化输出格式。
- 使用 ATT&CK 检索结果限制候选 Tactic/Technique。
- 将 Action 表达为目标、约束、期望输出和风险的任务契约。
- 对模型输出进行 JSON Schema、授权范围和风险策略校验。
- 使用 Mock Planner 保障离线测试和演示稳定性。

**退出条件**：输入“发现授权网段的资产和服务”可以生成合法 PTT 树；非法技术、越界目标或缺失输出契约会被拒绝。

### 阶段 5：执行编排、租约与动态重编排

**目标**：把 PTT、Agent、MCP 和黑板串成闭环。

**工作内容**：

- Router 根据能力、目标类型、负载和风险选择 Agent。
- 将阶段 3 的单次调用 Lease 检查纳入任务编排，冲突时挂起或切换任务。
- 记录 Session 状态、重试、取消和结果。
- 将 Agent 结果归一化并写回黑板。
- 根据黑板态势增量触发后续任务、剪枝不可行路径。
- 将阶段 3 的最小人工批准门禁扩展为高风险节点的 HITL 状态机。

**退出条件**：信息搜集 Agent 发现网络事实后，系统能自动生成并执行拓扑任务；重复资源任务会被 Lease 拒绝；高风险任务不会绕过审核。

### 阶段 6：演示界面与报告

**目标**：让完整链路可观察、可复核、可演示。

**工作内容**：

- 展示项目、授权范围和任务树。
- 展示 Agent 注册、调用状态和 Session 日志。
- 展示黑板中的资产、服务、网络关系和事实版本。
- 展示证据引用、风险状态和审计事件。
- 生成拓扑和发现报告。

**退出条件**：按照演示脚本可以从创建项目走到报告，任一事实都能追溯来源 Agent 和 Evidence。

### 阶段 7：集成验证与原型冻结

**目标**：确认闭环可靠，并记录后续研究和工程工作。

**工作内容**：

- 执行端到端测试和失败路径测试。
- 验证范围越界、Schema 错误、超时、Lease 冲突和 HITL 拒绝。
- 记录攻击链完整性、任务成功率、重复执行率、冲突率和黑板更新延迟。
- 更新架构图、运行说明和当前进度。

**退出条件**：演示环境可重复启动，关键验收场景有测试证据，已知限制写入进度文档。

## 5. 推荐代码边界

实现时按职责拆分，不把所有逻辑塞进一个 Agent 或 API 文件：

```text
src/
  domain/          # PTT、Fact、Evidence、Lease 等领域对象
  blackboard/      # 黑板存储、查询、事件和版本
  agents/          # Registry、Router、Session、Agent 适配器
  mcp/             # Gateway、Transport、Schema、审计
  planner/         # LLM Provider、ATT&CK 检索、PTT 编排
  policy/          # 授权范围、风险策略、HITL
  reporting/       # 事实投影、拓扑和报告
  api/              # 对外 HTTP 接口
tests/
docs/
```

实际目录可根据选定技术栈调整，但模块之间的职责边界必须保持。

## 6. 每个阶段的开发规则

1. 先更新领域契约或测试，再实现行为。
2. 每个阶段结束时运行该阶段的最小验收命令。
3. 不为了演示绕过授权、策略、租约和审计链。
4. 新增能力必须说明它写入黑板的事实类型和证据来源。
5. 每次完成一项工作，都要同步更新 `docs/开发进度.md`。
6. 任何架构决定或范围变化都记录在进度文档的“决策记录”中。
7. 每个阶段任务 Agent 在修改代码前，必须先向用户说明实现方案并提问：如果由它完成任务会如何开发、本阶段有哪些设计问题需要讨论和敲定；用户确认后才能修改代码。
8. 最高优先级是大约一周内交付可在靶场验证高危漏洞、RCE 或 shell 上传利用的 Demo；不为生产级能力牺牲主闭环进度。
